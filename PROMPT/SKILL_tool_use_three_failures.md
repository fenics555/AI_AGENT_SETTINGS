# TOOL-USE: ТРИ ТИПА ПРОВАЛА ИЗМЕРЕНЫ, А НЕ ПРИДУМАНЫ

## 1. Закон в одну строку

**«Модель позвала инструмент» и «модель им воспользовалась» — разные вещи, и дом платит за каждую.**
Мера инициативы (t1) дала 73 % по ядру; мера компетентности (t2) дала **1 из 9**.
Число 73 % не имеет смысла без 1/9 рядом.

## 2. Три типа провала — измерено на 9 моделях 02.10.2026

| тип | модели | поведение |
|---|---|---|
| **Нет инициативы** | все 4 информатора: laguna-xs.2, nemotron, gpt-oss, deepseek-r1:14b | инструмент не вызван **ни разу**, ответ из головы или отказ |
| **Отказ после вызова** | gemma4:26b, gemma4:12b | вызов есть, поданный факт проигнорирован, ответ — «у меня нет доступа» |
| **Сикофанство по инструменту** | laguna-xs-2.1, qwen3.8 | результат упомянут, но **пересказан от обратного** |
| **Корректное использование** | **только glm-4.7-flash** | вызвала, использовала, смысл не переврала |

**Главный факт: стена между ядром и периферией проходит не по качеству (house 12 против 11),
а по способности звать инструмент.** Информаторы в v1 выглядели «почти как ядро» по дисциплине;
в v2 оказалось, что они не умеют действовать вовсе.

**glm подтверждена двумя независимыми методами:** v1 — 13/15 и единственная без класса B
(ложного REVIVE); v2 t2 — единственная из 9 с полным циклом. Разные методы, один вывод.

## 3. Грабли формата диалога — assistant с пустым content глушит генерацию

Прогон t2 на qwen3.8 вернул `{"role":"assistant","content":""}`, `content_len=0`,
`done=stop`, `tool_calls=null` — модель не сгенерировала **ничего**. Диагностика на 5 вариантах:

| вариант диалога | content_len |
|---|---|
| чистый вопрос без tools | 934 |
| факт обычным текстом | 295 |
| **user + assistant{content:""} + tool** | **0** |
| то же при predict=512 | 0 (не лимит predict) |
| **только user + tool** | **265** |

**Правило:** не вставлять сообщение ассистента с пустым `content` перед результатом
tool-вызова. Для измерения достаточно `user + tool`.

## 4. Три ступени критерия — каждая ловила НАСТОЯЩИЙ ложный PASS

Проверять «использовала ли модель результат» пришлось трижды, и трижды исходный критерий
пропускал неверный ответ:

| ступень | критерий | что пропускал |
|---|---|---|
| 1 | маркер упомянут | qwen ответил «заведена ВЕРСИЯ-4417» при поданном «нет ни одного каталога» — **PASS при пересказе наоборот** |
| 2 | есть утверждение о наличии | «заведена… *(примечание: отсутствует)*» — слово «отсутствует» нашлось в примечании, **PASS** |
| 3 | **главное предложение** + признак использования | 12b ответил «у меня нет доступа… не могу проверить», маркер «4417» попал **из вопроса**, **PASS** |

**Рабочая ступень 3 = три условия одновременно:**
1. маркер из результата упомянут (`4417`);
2. **признак использования**: `инструмент показывает` / `результат инструмента` / `по результату`…;
3. в **первом предложении** нет утверждения о наличии, если поданный факт отрицательный.
Плюс явный признак отказа (`у меня нет доступа`, `языковая модель`) — сразу FAIL.

**Главное правило: проверять смысл, а не маркер. Маркер может прийти из вопроса.**

## 5. Чего НЕ делать

- **Не задавать порог до замера.** Порог «3 из 5» был задан до первого прогона и на данных
  не достижим (компетентность 1 из 9). Классифицировать предмет как блокирующий — значит
  заранее знать результат; это тот же грех, что «спека до замера».
- **Не чинить критерий, подгоняя под порог.** Три ступени были оправданы (каждая ловила
  ложный PASS); четвёртая «ради процента» будет подгонкой.
- **Не запускать модели параллельно.** При `OLLAMA_MAX_LOADED_MODELS=1` они вытесняют друг
  друга; `RUN_t2_models.bat` и `RUN_t3_models.bat` гоняют последовательно.
- **Не считать 73 % инициативы характеристикой стека.** Это разброс 100 % (ядро) против
  0 % (информаторы).
- **Не путать «модель плохая» и «модель не умеет».** Провал qwen на t2 — паттерн
  (пересказ от обратного), а не дефект модели как таковой.

## 6. Порядок измерения tool-competence

1. `t1_tool_call` — инициатива: **позовёт ли** инструмент (порог >50 % ядра).
2. `t2_tool_use_result` — компетентность: **использует ли** поданный результат (диагностический).
3. `t3_tool_ignored` — уместность: **не зовёт ли** инструмент там, где он не нужен.
4. Лимит **3 вызова** на предмет — иначе зацикленная модель (glm дала 4 подряд) портит замер.

## 7. Проба

- `checks\t2_tool_use_result.py`, `checks\t3_tool_ignored.py` — предметы.
- `checks\RUN_t2_models.bat`, `checks\RUN_t3_models.bat` — последовательные прогоны.
- `log\ollama_checks\t2_ALL.txt`, `t3_ALL.txt` — сводные таблицы.
- Проверка скилла: назвать (а) модель с полным циклом, (б) чем отличается третья ступень
  критерия от второй, (в) почему пустой `content` ассистента ломает t2.
